# spec-dev

**规范驱动开发（Spec-Driven Development）** —— 一个 Claude Code Skill，将新功能、跨模块改造和接口变更拆解为可确认、可追踪、可验证的开发流程。

## 适用范围

适合以下场景：

- 新功能开发；
- 跨模块重构或架构调整；
- API、数据结构或数据库 Schema 变更；
- 需要明确验收标准、用户评审和多步实现的改动；
- 用户明确要求使用 Spec-Driven Development。

简单拼写或文档修正、低风险单文件重构、明确范围的小型 Bug 修复和咨询类请求，不要求强制生成完整 Spec；但用户明确要求使用本 Skill 时除外。

## 安装

**克隆到 Claude Code 技能目录：**

```bash
# macOS / Linux
git clone https://github.com/libo1248/spec-dev.git \
  ~/.claude/skills/spec-dev

# Windows (PowerShell)
git clone https://github.com/libo1248/spec-dev.git `
  "$env:USERPROFILE\.claude\skills\spec-dev"
```

## 使用

在 Claude Code 中调用：

```text
/spec-dev
```

也可以在请求中明确要求使用 `spec-dev` Skill，例如：

```text
使用 spec-dev，为用户登录功能生成需求、设计和任务拆解。
```

Skill 开始执行前会检查项目规则、工作区状态以及已有的测试和构建命令。默认不会自动执行 Git commit、push、发布或创建 Pull Request。

## 核心流程

流程必须按顺序执行，不能跨越阶段。每个 Pause 点都需要用户回复“确认”或“继续”后才能进入下一阶段。

| Phase | 产出 | 关键内容 |
|-------|------|----------|
| **0. 执行前检查** | 项目上下文 | 读取项目规则、检查工作区、识别验证命令、保护用户已有修改 |
| **1. 需求规格** | `requirements.md` | User Stories、功能边界、非目标、业务规则、非功能需求和带编号的 AC；**Pause 1 等待确认** |
| **2. 架构设计** | `design.md` | 模块依赖、Schema、API 成功/失败契约、安全、迁移、回滚、可观测性和流程图；**Pause 2 等待确认** |
| **3. 任务拆解** | `tasks.md` | 原子化 Checklist、AC/Design 追溯、任务依赖和验证方式；**Pause 3 等待确认** |
| **4. 编码-测试-自愈** | 代码 + 测试记录 | 单线程逐 Task 实现，运行定向验证；代码错误最多自愈 3 次，超限熔断上报 |
| **5. 最终收尾** | 验收结果 | 全量测试、Lint、类型检查、构建、AC 验收和相关文档更新 |

## Pause 规则

- 用户提出修改意见时，先修改当前阶段文档，再次停在同一个 Pause 点；
- 用户只确认部分内容时，视为尚未确认；
- “继续”表示接受当前阶段内容并进入下一阶段；
- 未收到明确的“确认”或“继续”前，不得生成下一阶段产物或开始编码。

## Spec 目录结构

运行 `/spec-dev` 后，会在项目的 `docs/specs/` 下按**日期 + 功能名**创建或复用目录：

```text
docs/specs/
└── 20261030-用户登录/        # YYYYMMDD-功能名
    ├── requirements.md       # Phase 1：需求规格
    ├── design.md              # Phase 2：架构设计
    └── tasks.md               # Phase 3/4：任务清单与执行记录
```

目录名会转换为安全名称，仅允许中文、英文、数字、`-` 和 `_`。同日同名目录优先复用，不会直接覆盖已有内容；确需创建独立 Spec 时会追加序号或短标识。

> **约定**：所有 Phase 产出的 Spec 文件统一放在对应目录中，不分散在 `docs/specs/` 根目录。

## Task 追溯格式

每个 Task 都应关联需求、设计和验证方式：

```md
- [ ] Task 1: 增加登录接口
  - Requirements: AC-01, AC-02
  - Design: §3.1, §4.2
  - Depends on: None
  - Verify: `npm test -- auth`
  - Scope: API handler、参数校验和单元测试
```

只有实现符合已确认设计、相关验证通过、对应 AC 已覆盖且没有阻塞错误时，Task 才会在 `tasks.md` 中标记为 `[x]`。

## 测试与自愈规则

Skill 会优先使用项目规则、CI 配置和项目脚本中定义的测试、Lint、类型检查和构建命令，而不是仅根据项目类型猜测命令。

测试失败后会先分类处理：

- 代码或实现错误：进入自愈循环；
- 测试断言与已确认需求冲突：暂停并报告；
- 测试本身错误：修复测试或请求确认；
- 依赖、环境、服务、凭证或网络问题：标记为阻塞，不反复修改业务代码；
- 疑似不稳定测试：有限重跑并记录结果，不使用无限重试掩盖问题。

每个 Task 单独计算修复次数。首次验证失败不计入次数；每次针对失败结果完成一次修复后计数加一，最多允许 3 次修复。第 3 次修复后仍失败时，停止当前 Task 及后续自动修改，并报告失败命令、关键错误、已尝试修复和建议的人工处理方向。

如果项目没有自动化测试，必须记录人工验证步骤和未覆盖风险，不能将“没有测试”视为测试通过。

## 最终验收

进入 Phase 5 前，`tasks.md` 中的所有 Task 必须已标记为 `[x]`。最终收尾包括：

- 运行全量测试套件；
- 运行适用的全量 Lint、类型检查和构建；
- 逐项检查 Acceptance Criteria；
- 检查迁移、配置、部署、兼容性和回滚说明；
- 按项目约定更新 README、变更日志、API 文档或运维文档；
- 汇总修改文件、验证命令、测试结果、已知风险和未完成事项。

如果全量回归失败，不得报告“开发完成”，必须明确失败原因、影响范围和下一步建议。
