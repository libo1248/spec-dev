# spec-dev

**规范驱动开发（Spec-Driven Development）** —— 一个 Claude Code Skill，将新功能、跨模块改造、接口或数据结构变更，以及需要多步实现、明确验收标准或用户评审的任务拆解为可确认、可追踪、可验证的流程。

## 适用范围

适合以下场景：

- 新功能开发；
- 跨模块重构或架构调整；
- API、数据结构或数据库 Schema 变更；
- 安全或权限行为变更；
- 需要多步实现、明确验收标准或用户评审的改动；
- 用户明确要求使用 Spec-Driven Development。

简单拼写、格式或文档修正、低风险单文件重构、不涉及接口/数据结构/安全/权限变更的小型 Bug 修复、咨询类请求，以及不涉及业务行为的工具配置调整，可以直接处理；用户明确要求使用本 Skill 时除外。

## 使用

```text
/spec-dev
```

也可以在请求中明确要求使用 Skill：

```text
使用 spec-dev，为用户登录功能生成需求、设计和任务拆解。
```

需要完整流程时明确说明：

```text
使用 spec-dev 的完整模式，按阶段确认后再实现。
```

Skill 开始执行前会读取项目规则、检查工作区状态、识别验证命令，并说明所选模式和依据。不会覆盖用户已有修改，也不会默认执行 Git commit、push、发布或创建 Pull Request。

## 完整模式与轻量模式

| 模式 | 适用条件 | 规格产物 | 确认方式 |
|------|----------|----------|----------|
| **完整模式** | 新功能、跨模块重构、接口/数据结构/Schema、安全或权限变更；或用户明确要求完整流程 | `requirements.md`、`design.md`、`tasks.md` | 需求、设计和任务拆解分别确认 |
| **轻量模式** | 范围单一、低风险、不涉及完整模式条件的任务 | 合并为 `spec.md` | 编码前一次确认需求、简化设计和任务整体 |

两种模式都保留需求边界、非目标、带编号的 AC、设计到任务的追溯、验证方式、工作区保护、自愈上限和最终验收。轻量模式只合并 Phase 1–3 的文档与确认，不省略 Phase 4 和 Phase 5。

不确定风险时使用完整模式；用户要求完整流程时不得降级。执行中发现轻量模式不再适用时，暂停实现、迁移有效内容到完整模式文件，并重新确认受影响阶段。

需求和设计模板中的不适用项可标记为 `N/A` 并简述原因，不必虚构内容填满模板；需求边界、非目标、AC、实现路径、追溯和验证方式不能整体省略。轻量模式允许合并章节和简短描述，无需为简单流程强制绘图。

## 核心流程

以下为完整模式。阶段按顺序执行，每个 Pause 都必须等待用户明确接受当前产物。

| Phase | 产出 | 关键内容 |
|-------|------|----------|
| **0. 执行前检查** | 项目上下文 | 项目规则、工作区保护、验证命令、模式选择、需求澄清 |
| **1. 需求规格** | `requirements.md` | 目标、范围、非目标、业务规则、假设、非功能需求和带编号的 AC；**Pause 1** |
| **2. 架构设计** | `design.md` | AC 实现路径、模块依赖、API 成功/失败契约及适用的安全、迁移、回滚和验证策略；**Pause 2** |
| **3. 任务拆解** | `tasks.md` | 原子任务、稳定编号、AC/Design 追溯、依赖和验证方式；**Pause 3** |
| **4. 编码-测试-自愈** | 代码 + 验证记录 | 单线程逐 Task 实现、定向验证；每个 Task 最多修复 3 次，超限停止并报告 |
| **5. 最终收尾** | 验收结果 | 适用的全量回归、AC 验收、文档同步和延期/取消说明 |

轻量模式在同一 `spec.md` 中依次编写需求、简化设计和任务清单，整体确认后进入 Phase 4；状态、验证和变更记录也保存在该文件中。

### 待确认事项

- **阻塞性事项**：影响业务行为、数据模型、架构或验收。先澄清，可以整理不依赖答案的内容，但不得进入受阻塞阶段。
- **非阻塞性事项**：可以在低风险假设下继续。记录依据、影响范围和最迟确认阶段；阶段确认不自动确认所有待确认项，应明确哪些假设被接受。
- 假设升级为关键问题时，暂停相关工作并请求确认。

## Pause 规则

- 不要求固定关键词：当前 Pause 上下文中的“确认”“继续”“没问题，往下做”“这个方案可以”等明确接受表达均有效。
- 仅表示理解、询问内容、提出保留意见或只确认部分内容，不视为完整确认；语义不清时请求澄清。
- 用户提出修改意见时，先修改产物，再停在同一 Pause；要求修改不等于确认尚未修改完成的产物。
- 确认只覆盖当前展示的产物和范围，不自动覆盖下一阶段或后续变更。
- 暂停时说明文件、主要内容、待确认事项和下一阶段；实际确认的范围、日期和用户表达记录在 Spec 中。

## Spec 目录结构

在项目的 `specs/` 下按**日期 + 功能名**创建或复用目录。

完整模式：

```text
specs/
└── 20261030-用户登录/
    ├── requirements.md       # 需求规格
    ├── design.md             # 架构设计
    └── tasks.md              # 任务与执行记录
```

轻量模式：

```text
specs/
└── 20261030-低风险改动/
    └── spec.md               # 需求、简化设计、任务与执行记录
```

目录名只允许中文、英文、数字、`-` 和 `_`，不得改变目录结构。同日同名目录先判断是否为同一任务；同一任务优先读取并复用，独立任务追加序号或短标识，不直接覆盖已有内容。

所有 Spec 产物放在对应任务目录中，不分散在 `specs/` 根目录。

## Task 追溯与状态

```md
- [ ] T-001: 增加登录接口
  - Requirements: AC-01, AC-02
  - Design: §3.1, §4.2
  - Depends on: None
  - Verify: `npm test -- auth`
  - Scope: API handler、参数校验和单元测试
```

示例命令仅演示格式，实际执行使用项目已有命令。新任务采用稳定的 `T-001`、`T-002` 编号，插入、排序、延期或取消时不重排、不复用；已有 Spec 的编号保留，避免破坏引用。执行顺序由依赖和列表顺序确定，而非编号大小。

| 标记 | 含义 |
|------|------|
| `[ ]` | 待处理、进行中或阻塞；阻塞原因另行记录 |
| `[x]` | 已完成且验证满足条件 |
| `[~]` | 经用户明确确认延期，移出本次交付范围 |
| `[-]` | 经用户明确确认取消，移出本次交付范围 |

`[~]` 和 `[-]` 为文本标记，不依赖编辑器的复选框渲染。延期/取消记录原因、用户确认内容、日期、关联 AC 和依赖影响，不删除原任务，不假装完成，也不能用于掩盖验证失败。

当前范围内的 AC 必须由有效任务覆盖；任务不能依赖未完成的延期/取消任务。只有实现符合设计、相关 AC 验证完成、适用检查通过且无阻塞时，才实际保存 `[x]` 和验证结果。

## Spec 变更与恢复

任一阶段发现已确认规格需要调整时：

1. 暂停当前及后续实现，保留工作区，不自动回滚。
2. 说明原因、候选方案及对 AC、设计、任务依赖、已完成代码/测试和验证结果的影响。
3. 更新相关 Spec，标记候选内容“待确认”，保留原确认记录、稳定编号和有效信息，记录日期与原因。
4. 回到最早受影响的 Pause：需求变更回到 Pause 1，仅设计变更回到 Pause 2，仅任务调整回到 Pause 3；轻量模式回到统一 Pause，超出适用范围则升级。
5. 确认后按顺序更新并重新确认受影响的下游产物；未受影响的确认保留，尚未生成的产物按正常流程生成和确认。
6. 延期/取消在用户明确确认后才修改状态；同步确认关联 AC 的范围变化并修正下游依赖。
7. 因变更失效的已完成任务重新标为 `[ ]`，保留原验证记录；恢复后重新执行受影响验证。

## 测试与自愈规则

验证命令优先依据项目规则、贡献指南、CI 和项目脚本，不仅凭项目类型猜测。逐 Task 运行定向验证及项目必需检查，收尾时进行适用的全量回归。

测试失败先分类：

- 实现错误：进入自愈循环；
- 断言与已确认需求冲突：暂停，按 Spec 变更流程处理，不直接修改预期；
- 测试本身错误：不改变已确认行为的前提下修复，无法判断时请求确认；
- 环境、依赖、服务、凭证或网络问题：标记阻塞，不反复修改业务代码；
- 疑似不稳定测试：有限重跑并记录，不以无限重试代替修复。

每个 Task 单独计算修复次数：首次失败不计数，每次针对失败完成一次修复计数加一，最多 3 次。第三次修复后仍失败，停止当前及后续自动修改，报告命令、关键错误、已尝试修复、工作区状态和建议方向。暂停后不能通过重启 Task 自动清零，需要用户明确指示下一步。

没有自动化测试时，必须实际执行人工验证，记录步骤、结果和未覆盖风险；只有验证计划或“没有测试”，不算通过。

## 最终验收

本次交付范围内所有 Task 必须为 `[x]`；其他任务只能是已确认并同步调整范围/依赖的 `[~]` 或 `[-]`。存在未处理或阻塞的 `[ ]` 时，不能进入最终收尾。

收尾包括：

- 适用的全量测试、Lint、类型检查和构建；无自动化测试时执行并记录人工回归；
- 对本次范围内 AC 逐项验收，单独列出移出范围的 AC 和确认依据；
- 检查适用的迁移、配置、部署、兼容性和回滚说明；
- 同步相关 README、变更日志、API 和运维文档；
- 汇总文件、验证命令、结果、风险、延期/取消和剩余事项。

全量回归失败或验收未通过时，不得报告“开发完成”。定位到具体任务后重新标为 `[ ]`、记录原因，按 Phase 4 修复并再次回归；规格改变时先重新确认，自愈上限仍有效。

存在延期/取消时，只能报告“本次已确认范围完成”并列出排除项，不暗示原始全部需求已交付。全部任务被延期/取消时，报告“本次无实现交付，范围已调整”。
